# MagMutual Actuarial/DS/ML Infrastructure

## Overview

This repository is the central hub for all data science, machine learning, and AI projects at MagMutual. It contains:

- **Feature Store** - Centralized, versioned feature library with 3 layers (production, development, candidate)
- **Model Registry** - Centralized, versioned model catalog with 3 layers (production, development, base/AutoML)
- **AI Projects** - Space for exploratory AI/ML projects with standard dev/prod structure
- **Monitoring & Observability** - Automated monitoring for production features and models

All data is sourced from Snowflake, with feature engineering, storage, and model inference orchestrated through Snowflake Cortex.

## Architecture Overview

### Three-Layer Feature Store

#### 1. **Production Features** (`feature-store/src/production/`)
Features actively used in production models. Features in this layer:
- Have been thoroughly evaluated and tested
- Are monitored continuously for data quality and drift
- Have version numbers (1.0, 1.1, 2.0, etc.)
- Are locked and require formal approval to modify
- Include timestamps for last evaluation/finalization and last data refresh
- SLA: Data refresh ≤ 24 hours

#### 2. **Development Features** (`feature-store/src/development/`)
Features currently being evaluated by data scientists for potential production use. Features in this layer:
- Are being tested in dev models
- May change frequently during development
- Have version numbers (1.0, 1.1, etc.)
- Include evaluation status and results
- Include timestamps for last evaluation and last data refresh

#### 3. **Candidate Features** (`feature-store/src/candidate/`)
Features proposed for future evaluation. Features in this layer:
- Are documented but not yet in active use
- Include definition, lineage, and engineering logic
- Are queued for evaluation in future models
- Include initial timestamps
- No active monitoring yet

### Three-Layer Model Registry

#### 1. **Production Models** (`model-registry/src/production/`)
Models actively serving predictions in production. Models in this layer:
- Have passed rigorous validation and testing
- Are monitored continuously for performance and drift
- Have version numbers (1.0, 1.1, 2.0, etc.)
- Are locked and require formal approval to modify
- Include comprehensive model cards with all metadata
- Include timestamps for last evaluation/finalized and last data refresh
- SLA: AUC > 0.85, Latency < 20ms

#### 2. **Development Models** (`model-registry/src/development/`)
Models currently being built and tested by ML engineers and data scientists. Models in this layer:
- Are in active development by team members
- May change frequently during experimentation
- Have version numbers (1.0, 1.1, etc.)
- Include model cards with current state
- Include timestamps for last evaluation and last data refresh

#### 3. **Base/AutoML Models** (`model-registry/src/base/`)
Models automatically generated by the system via AutoML. Models in this layer:
- Are created by evaluating current feature sets against target variables
- Serve as performance baselines for comparison
- Can be promoted to dev or prod with approval
- Include comprehensive model cards
- Enable rapid experimentation

### Automated Monitoring

**Production Features:**
- Automated data quality checks (nulls, range, cardinality)
- Drift detection (statistical tests)
- Freshness monitoring (last refresh time)
- Alerts → Slack #ml-alerts

**Production Models:**
- Performance tracking (AUC, precision, recall)
- Prediction distribution monitoring
- Feature drift detection
- Performance SLA violations
- Alerts → Slack #ml-alerts + PagerDuty

## Key Requirements

### Versioning

Both features and models use semantic versioning:

**Features:**
- **1.0** - Initial version
- **1.1** - Bug fixes or minor adjustments (same semantics, refined calculation)
- **1.2** - Continued minor improvements
- **2.0** - Major changes (new data source, new calculation method, algorithm change)

**Models:**
- **1.0** - Initial production version
- **1.1** - Hyperparameter tuning (same algorithm, improved performance)
- **1.2** - Additional features added to same model
- **2.0** - Different algorithm or major retraining
- **3.0** - Complete model redesign

When promoting to production, use the version as git tag:
- `feature_001_customer_age-v1.2`
- `model_2026_q3_churn-v1.0`

### Timestamps

All production features and models track **two timestamps:**

1. **Last Evaluated/Finalized** (UTC format: YYYY-MM-DD HH:MM:SS UTC)
   - When the feature/model was last validated and approved
   - Updated when promoted to a new layer
   - Example: `2026-08-01 14:30:00 UTC`

2. **Last Data Refresh** (UTC format: YYYY-MM-DD HH:MM:SS UTC)
   - When the underlying source data was last updated in Snowflake
   - Tracks freshness for monitoring SLAs
   - Example: `2026-08-07 02:15:00 UTC`

These timestamps enable:
- Monitoring of data staleness
- SLA tracking and compliance
- Automated alerts if refresh is overdue
- Complete audit trail

## Contributing Workflow

### For Data Scientists - Adding a Feature

1. **Create feature documentation** using `feature-store/docs/TEMPLATES/feature_template.md`
2. **Name file**: `feature_###_feature_name.md` (e.g., `feature_001_customer_age.md`)
3. **Fill all sections**:
   - Metadata with version 1.0
   - Feature definition, data type, granularity
   - Data lineage with SQL
   - Univariate statistics
   - Initial timestamps
4. **Submit to development layer**:
   - Create feature branch: `feature/feature_###_name`
   - Add to `feature-store/src/development/features/`
   - Create PR to `develop` branch
5. **Validation**:
   - Data Science team reviews
   - Minimum 1 approval (24-hour window)
   - Merge to `develop`
6. **Promote to Production**:
   - Create release branch: `release/feature_###_v1.0`
   - Update layer to `production`
   - Update timestamps
   - Create PR to `main`
   - Require 2 approvals (48-hour window)
   - Tag version and push
7. **Set up monitoring**:
   - Configure automated checks
   - Set up drift detection alerts

### For ML Engineers - Adding a Model

1. **Create model card** using `model-registry/docs/TEMPLATES/model_card_template.md`
2. **Name file**: `model_[YYYY]_[period]_[name].md` (e.g., `model_2026_q3_churn_prediction.md`)
3. **Fill all sections**:
   - Metadata with version 1.0
   - Model intent and target variable
   - Features selected (from production feature store)
   - Algorithm and hyperparameters
   - Validation metrics
   - Initial timestamps
4. **Submit to development layer**:
   - Create feature branch: `feature/model_[name]`
   - Add to `model-registry/src/development/models/`
   - Include training code (optional)
   - Create PR to `develop` branch
5. **Validation**:
   - ML Engineering team reviews
   - Minimum 1 approval (24-hour window)
   - Merge to `develop`
6. **Promote to Production**:
   - Create release branch: `release/model_[name]_v1.0`
   - Update layer to `production`
   - Update timestamps
   - Create PR to `main`
   - Require 2 approvals from: ML lead, Product Manager, VP Data Science
   - Verify monitoring infrastructure
   - Tag version and push
7. **Set up monitoring**:
   - Configure performance checks
   - Set up SLA tracking
   - Create monitoring dashboard

## Snowflake Integration

All features and models are backed by Snowflake:

- **Raw Data**: Stored in `raw_data` schema (daily refresh)
- **Feature Storage**: Materialized in Snowflake via Cortex
- **Model Storage**: Registered with Snowflake Cortex for inference
- **Monitoring**: Automated checks via Cortex jobs

### Data Refresh Schedule
- Raw data: Daily from source systems
- Production features: Daily (2 AM UTC)
- Batch predictions: Daily (3 AM UTC)
- Monitoring checks: Hourly

## Governance & Approval

### Development Layer (Develop Branch)
- **Reviews Required**: Minimum 1 approval
- **Review Team**: Data Science or ML Engineering team
- **Timeline**: 24-hour review window
- **Merge**: After approval

### Production Layer (Main Branch)
- **Reviews Required**: Minimum 2 approvals
- **Approval Chain**:
  - ML/Data Science team lead
  - Platform/Monitoring team
- **Timeline**: 48-hour review window
- **Requirements**:
  - All SLAs verified
  - Monitoring infrastructure confirmed
  - Data quality checks passing
  - No data privacy/security issues
- **Merge**: After approvals
- **Tag**: Version tag required (e.g., `feature_001_v1.0`)
